## Project name

THREADROOM

## Tagline

Compare something new with something you already love.

## Inspiration

A possible purchase competes with clothes already in a wardrobe. THREADROOM explores that comparison in one small fitting workspace: keep the same person photo as a reference, give the owned alternative equal attention, and add the price and expected use behind the decision. The demonstrated person and garments are cleared synthetic inputs. Ownership and the sample price are fictional scenario labels, not a retailer relationship or claim of actual ownership.

## What it does

Choose two garments, use the same consented person input, then compare the genuine YouCam outputs in A/B or before/after views. The interface includes English, Traditional Chinese and Japanese. Add your own price, expected wears and a note; cost per wear is simple division, not an AI prediction.

The controlled local test completed one native smoke and one two-look browser action: three real `cloth-v3` upper-body tasks in total. Both local browser results were Ready and loaded at 1024 x 1536. After public activation, one consented two-look action also returned both Ready outputs loaded at 1024 x 1536, bringing the total to five tasks. Desktop local checks exercised the comparisons and three-language DOM. Entering price 68 and 50 expected wears displayed 1.36 per wear.

The actual comparison PNG downloaded successfully, and the notes JSON was 749 bytes with no images or URLs. Downloads are explicit and local; the app has no checkout, public gallery or automatic posting. Generated looks are visual impressions, with no size, comfort, fabric or physical-fit guarantee.

## How we built it

The buildless client uses HTML, CSS and JavaScript with self-hosted fonts. A small PHP service keeps credentials server-side, validates/strips image metadata, uploads sanitized inputs, creates asynchronous YouCam tasks and returns session-owned private results. It checks available units and feature cost, reserves a bounded budget in a locked ledger and never automatically repeats an uncertain chargeable POST.

Codex assisted implementation, and OpenAI image generation supplied the three original synthetic sample inputs. Their provenance is documented in [ASSETS.md](ASSETS.md); those inputs are distinct from the later genuine YouCam results. Original application code and documentation use MIT; fonts, images and provider outputs retain their separate conditions.

The public application source and CI are linked below. The recorded r3 deployment matched 23 application files to that source and passed 19 public HTTPS checks with live disabled. Later local provider/browser evidence and public activation are separate from those historical deployment checks and the 21 fake-provider cases. Activation at 08:28:23 UTC on 30 October 2026 retained all 23 application files; it created no generation itself. The production pool enables live mode with a two-task session cap, 150-task/300-unit global ceilings and provider reserve 300.

## Challenges we addressed

We kept source images and completed provider outputs distinctly labelled, treated uncertain requests as a billing issue, and preserved unit reservations across errors and Clear. Local PHP initially needed an explicit trusted CA bundle; strict certificate verification stayed enabled. A read-only snapshot after the three local tasks, before public activation, reported 1034 available units, cost 2 per result and reserve 300. That is a historical observation; no balance was measured after the public pair. Without a pre-generation API snapshot, scheduled units are not a measured debit.

The browser Clear attempt did not visibly complete. A fresh foreign session received 404 for a result, which proves session isolation rather than successful deletion. The later public try-on is verified; a verified cleanup procedure remains separate. Use cleared synthetic samples until private support and retention/cleanup verification are complete.

## What we learned

A real provider outcome, a passing fake-provider suite and a public page loading are distinct pieces of evidence. The same applies to cleanup: a foreign-session denial is useful but cannot establish that the original session or provider data was erased. The design keeps those limits visible while leaving the purchase decision with the user.
